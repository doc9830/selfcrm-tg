# Архитектура SelfCRM

## Принципы

1. **Простота и работоспособность важнее «правильности ради правильности».** Никаких лишних
   зависимостей и абстракций.
2. **Личная CRM, локальные данные.** Нет бэкенда, нет авторизации.
3. **Первая цель — Telegram Mini App.** Приложение — обычное статичное SPA: то же самое
   собирается и под Capacitor WebView (Android), и открывается внутри Mini App без изменений
   в логике. Всё специфичное для Telegram изолировано в `src/telegram/`.

## Стек и обоснование

| Слой      | Выбор                                  | Почему                                                        |
| --------- | -------------------------------------- | ------------------------------------------------------------- |
| UI        | React 18 + TypeScript + Vite           | Быстрый dev-режим, типизация, простая сборка под WebView      |
| Роутинг   | собственный hash-роутер (`src/router.ts`) | Без зависимостей; hash-маршруты безопасны под `file://` в Capacitor и в WebView Telegram |
| Данные    | `KVStore` + `Database` (`src/db/`)     | Синхронно, надёжно, переживает перезапуск                     |
| Telegram  | `telegram-web-app.js` + типы в `src/telegram/webapp.ts` | Официальный скрипт вместо SDK-пакета: меньше зависимостей, всегда актуальная версия API |
| Офлайн    | `public/sw.js`                         | Оболочка страницы кэшируется: Mini App открывается без сети   |
| Тесты     | Vitest                                 | Быстрые unit-тесты ядра                                       |
| Стили     | чистый CSS                             | Mobile-first, без CSS-фреймворков                             |

### Почему не SQLite сразу

Требование — «локальная SQLite, если она решает задачу». Для **браузерного** dev-режима и WebView
наиболее подходящий встроенный аналог — простое key-value хранилище (`localStorage`), которое:

- не требует wasm/нативного моста,
- работает одинаково в браузере и Capacitor WebView,
- гарантированно сохраняет данные между запусками.

Хранилище вынесено за интерфейс `KVStore`, поэтому при переходе к Android-сборке его можно
заменить на SQLite (`@capacitor-community/sqlite`), реализовав тот же интерфейс, — без изменений
остального кода. Для объёма данных небольшой CRM (сотни записей) `localStorage` достаточно.

## Telegram Mini App

Отдельная схема: Telegram показывает кнопку, страница — статика на GitHub Pages, бот — только
точка входа. Ни бот, ни Pages не хранят данные CRM.

```text
Telegram-клиент
   │  inline-кнопка web_app (и кнопка меню)
   ▼
scripts/telegram-bot.mjs (@fastcrm_bot, локально)
   │  один раз: setMyCommands + setChatMenuButton
   ▼
https://doc9830.github.io/selfcrm-tg/   ← dist/ из .github/workflows/deploy-pages.yml
   │  index.html → telegram-web-app.js → src/main.tsx
   ▼
SelfCRM (React) → KVStore (localStorage) — все данные остаются на устройстве
```

| Файл                                | Роль                                                        |
| ----------------------------------- | ----------------------------------------------------------- |
| `src/telegram/webapp.ts`            | типы WebApp API и null-safe доступ (`getTelegramWebApp`, `isTelegramEnvironment`, `insideTelegramWebView`, `openExternalLink` и др.) |
| `src/telegram/environment.ts`       | `ready()`/`expand()`, размеры окна, тема клиента, BackButton |
| `src/telegram/cloudStorage.ts`      | промисная обёртка над `WebApp.CloudStorage` (Bot API 6.9+): чтение, запись, удаление ключей облака Telegram, доступность облака и её причина (`cloudStorageAvailability()`) |
| `src/components/TelegramShell.tsx`  | мост: связывает события Telegram с роутером и темой          |
| `index.html`                        | подключение `telegram-web-app.js`, CSP, тема до отрисовки    |
| `src/index.css`                     | `--safe-*` и `--tg-stable-height` вместо жёстких отступов    |
| `public/sw.js`                      | офлайн-оболочка страницы                                     |
| `scripts/telegram-bot.mjs`          | бот: `/start`, `/help`, `/whatsnew`, кнопка «Открыть SelfCRM» и кнопка меню (общая и в чате) |
| `.github/workflows/sync-from-selfcrm.yml` | перенос новых функций Android-версии: `scripts/sync-from-selfcrm.mjs` → ветка и PR с отчётом |
| `.github/workflows/ci.yml`          | типы, тесты и сборка на pull request                        |

Ключевое правило: **слой Telegram необязателен**. Любая функция `src/telegram/*` возвращает
`null` или `() => {}`, если `window.Telegram.WebApp` отсутствует, поэтому то же приложение
работает в браузере и в Android-сборке. Подробности, безопасность и диагностика —
[docs/TELEGRAM_ARCHITECTURE.md](./docs/TELEGRAM_ARCHITECTURE.md). Как переносить сюда новые
функции Android-версии — [docs/UPSTREAM_SYNC.md](./docs/UPSTREAM_SYNC.md).

## Модель данных

Сущности (`src/types.ts`):

- **Client** — имя, телефон, email, комментарий, адрес (опционально — кадастровый номер и координаты), дата создания, признак архива
  (`archived`, опционально — дата `archivedAt`).
- **Product** — название, артикул, цена, остаток, минимальный остаток, описание, себестоимость
  (`cost`, для расчёта прибыли) и тип позиции (`kind`: `product` — товар по умолчанию или
  `service` — услуга, не учитываемая на складе).
- **Order** — номер (`number`, сквозная нумерация), клиент, дата, статус, список позиций,
  список платежей (`payments`), напоминания (`reminders`) и комментарий.
- **OrderItem** — ссылка на товар (может быть null), название, цена и себестоимость (снимок
  на момент заказа), количество.
- **Payment** — платёж по заказу: сумма, дата, комментарий («Предоплата», «Наличные»…).
- **Reminder** — напоминание по заказу: вид (`kind`: `call`, `payment`, `product`, `other`),
  текст, срок (`dueAt`), дата создания и признак выполнения (`done`, `doneAt`).
- **StockMove** — движение товара: изменение остатка (`delta`), вид (`in` — поступление,
  `out` — расход, `adjustment` — корректировка, `order` — списание по заказу), причина
  («Заказ №42») и остаток после операции (`stockAfter`).
- **Contractor** — реквизиты исполнителя (название/ФИО, ИНН, ОГРН, КПП, телефон, email, адрес); хранятся в настройках и попадают в чек.
- **AddressEntry** — запись базы адресов (`db/addresses.ts`): кадастровый номер, полный адрес, координаты.

Связи:

- `Order.clientId → Client.id` (заказ может быть без клиента).
- `OrderItem.productId → Product.id` (опционально; название/цена/себестоимость сохраняются как
  снимок, поэтому удаление товара и изменение цен не ломают историю заказов).
- `Payment` — часть заказа: «оплачено» — сумма платежей, остаток — сумма заказа минус оплата.
- `Reminder` — тоже часть заказа: удаление заказа (или каскадное удаление заказов вместе
  с клиентом) уносит и напоминания, отдельных ссылок на заказ нет.
- `StockMove.productId → Product.id`; удаление товара удаляет и его историю.

Всё сериализуется в один JSON-снимок `DatabaseSnapshot` под ключом `selfcrm:data`.

## Слой хранения

- `kvstore.ts` — интерфейс `KVStore` (`getItem`/`setItem`/`removeItem`), реализации:
  `localStorageStore` (продакшн) и `MemoryStore` (тесты).
- `database.ts` — класс `Database`: CRUD для сущностей, связи, движение склада и его история,
  суммы, настройки, экспорт/импорт, сброс. Геттеры и сохранения работают с **копиями** объектов,
  чтобы внешний код не мог случайно изменить внутреннее состояние.
- Миграция старых данных (`migrate()` при загрузке и после импорта): заказам без номера
  присваивается сквозной номер по возрастанию даты, позициям без снимка себестоимости —
  себестоимость из каталога (0, если товар удалён), заказам без поля `payments` — пустой список,
  заказам без поля `reminders` — пустой список напоминаний.
  Так базы версий до 1.1.0 открываются без ручных действий.

## Клиенты: архив вместо удаления

Клиент не удаляется сразу — он уходит в **архив** (`Client.archived`), потому что каскадное
удаление ломает историю: вместе с клиентом исчезали бы его заказы, выручка и движения склада.

- `archiveClient(id)` ставит флаг и дату (`archivedAt`), не трогая заказы и остатки;
  `restoreClient(id)` снимает флаг.
- `getClients()` по умолчанию возвращает **только активных** — архивный клиент не появляется
  в списке и его нельзя выбрать при оформлении заказа; `getArchivedClients()` отдаёт архив
  для отдельной вкладки, а `getClient(id)` возвращает клиента всегда, поэтому имя не пропадает
  из карточки заказа и топа статистики (там архивный клиент помечается «(архив)»).
- Окончательное удаление доступно **только из архива** (`deleteClient`): заказы клиента
  удаляются, товары возвращаются на склад — как и раньше, с предупреждением в интерфейсе.
- Поле `archived` опционально, поэтому базы и резервные копии, созданные до его появления,
  читаются без миграции: отсутствие поля означает активного клиента.

Вид списка хранится в адресе: `/clients?archive=1` — архив (`clientsArchiveFromQuery` в
`utils/links.ts`), без параметра — активные. Переключатель — значок архива в шапке
(`components/Layout.tsx`): пока архив открыт, кнопка подсвечена (`.icon-btn-active` — тот же
приём, что `.nav-item-active` в нижнем меню), второе нажатие снимает выделение и возвращает
активных; чипов на экране больше нет, поэтому шапка — единственный переключатель. Заголовок
шапки в архиве — «Архив» (`App.tsx`). Карточка клиента (`screens/ClientDetail.tsx`) — кнопку
«В архив» у активного и «Восстановить»/«Удалить навсегда» у архивного; ссылка на карточку
помечается `?from=archive`, чтобы кнопка «Назад» вела обратно в архив (`clientLink`,
`clientCardBackFromQuery`).

## Движение склада

Сток привязан к позициям заказа со ссылкой на товар:

- «Зафиксированное» количество = сумма `qty` по товару для заказов со статусом, отличным от `cancelled`.
- При сохранении заказа остаток меняется один раз — на разницу между старой и новой версией
  (`applyOrderStock`), поэтому в истории движения нет «возврата» и повторного списания.
- При отмене и удалении заказа остаток возвращается (в истории — запись «Заказ №42 (отменён)»
  или «Удаление заказа №42»).
- Каждое изменение остатка попадает в историю товара (`stockMoves`) с причиной и остатком
  после операции (`applyStockDelta`).
- Услуги (`Product.kind === 'service'`) в движении склада не участвуют: количество не списывается
  при оформлении заказа и не возвращается при отмене или удалении, а сама позиция всегда доступна
  для добавления в заказ. В `database.ts` это проверяет хелпер `isService()`.

Ручные операции — `applyStockMove({ productId, kind, value, comment })`: `in` и `out` принимают
количество, `adjustment` — новый остаток (если он совпадает с текущим, движение не создаётся).
Где это в интерфейсе: экран **Склад** (`screens/Stock.tsx`) — список товаров с остатками, тап по
строке открывает экран товара (`screens/StockProduct.tsx`, маршрут `/stock/<id>`) со сводкой,
ручными операциями и всей историей. Блок учёта (`components/StockPanel.tsx`) живёт только там,
поэтому в карточке товара (`screens/Products.tsx`) остаток не меняется: стартовый остаток
задаётся один раз при создании товара (движение «Начальный остаток»). Остаток и история всегда
читаются из базы заново.

Массовые операции — `applyBulkStockMove({ kind: 'in' | 'out', items, comment })`: одна причина
на всю операцию, по одному движению на позицию и одна запись в хранилище. Услуги, неизвестные
позиции и нулевые количества пропускаются, функция возвращает число изменённых позиций.
Где это в интерфейсе: кнопки «Приход» и «Списание» на экране **Склад** (в `screens/Stock.tsx`,
над плашкой низкого остатка) открывают окно `components/BulkStockModal.tsx` — причина вводится
вручную, список позиций фильтруется поиском, и у каждой строки сразу виден будущий остаток.

Это гарантирует корректность при создании, редактировании, отмене и удалении заказов
(покрыто тестами).

**Ограничение.** История пишется с момента появления функции (версия 1.1.0): для заказов,
созданных раньше, движений в базе нет — восстановить их можно было бы только догадками,
поэтому приложение этого не делает.

## Функциональность без ограничений

Все функции приложения доступны сразу и без ограничений: клиенты, заказы, товары и склад,
чек в PDF, маршрут, адреса и резервные копии. Платных тарифов и переключателей нет.

## Резервное копирование

- Формат файла — версионируемый конверт (`db/backupFormat.ts`):
  `{ "format": "selfcrm-backup", "version": 1, "createdAt": …, "appVersion": "1.5.0",
  "app": {…}, "data": { снимок базы } }`.
  Ключи снимка (`clients`, `products`, `orders`, `stockMoves`, `settings`) продублированы в корне
  файла, поэтому копию читает и старая версия SelfCRM (Android-сборка ожидает снимок в корне), а
  импорт новых версий смотрит только на `data`. Формат `selfcrm` предыдущей версии и файлы без
  конверта (копии Android-сборки) читаются как свои. Файл с версией формата выше поддерживаемой
  отклоняется с понятным сообщением, а не импортируется частично.
- Что попадает в `data`: клиенты (включая архив), товары и услуги, заказы с позициями, оплатами и
  напоминаниями, история склада, реквизиты исполнителя и загруженная пользователем база адресов
  (демо-набор — нет). Токен бота, `initData`, тема оформления и служебные ключи хранилища в копию
  не попадают.
- Версионирование и миграции: `version` — версия формата файла, а не схемы данных. Импорт
  пропускает данные через `applyFormatMigrations` (цепочка «N → N+1»), поэтому будущее изменение
  структуры копии не потребует писать разбор заново; сейчас цепочка пустая — формат один.
- В `app` записываются версия приложения и платформа, а внутри Telegram — ещё `id` и имя
  пользователя: это подпись копии, а не ключ данных (у клиентов, заказов и товаров свои id).
- Экспорт файла: `SelfCRM_backup_<дата>_<время>.json`. В браузере — обычное скачивание
  (blob + `<a download>`), на Android — запись в `Directory.Cache` через `@capacitor/filesystem` и
  системное меню «Поделиться» (`@capacitor/share`): WebView игнорирует скачивание по ссылке, поэтому
  раньше нажатие «Скачать» на телефоне ничего не делало. PDF-чек отдаётся похожей схемой
  (`pdf/documents.ts` + `pdf/receiptDelivery.ts`): файл там, где клиент умеет его сохранить, и
  ссылка на страницу чека — там, где файл отдать нельзя. В Mini App Telegram blob-скачивание и
  `<a download>` не работают (клиент их
  игнорирует, а `WebApp.downloadFile` принимает только адреса `https:`), поэтому основная кнопка
  копии там — облако Telegram.
- Копия в облаке Telegram (`db/cloudBackup.ts` поверх `telegram/cloudStorage.ts`) — путь по умолчанию
  для Mini App: настройки → «Копия в облаке Telegram» → «Сохранить». Облако привязано к аккаунту, а не
  к телефону, поэтому копию можно восстановить на другом устройстве из того же мини-аппа. Хранится
  тот же конверт копии, порезанный на части по 3500 **байт** (ограничение `CloudStorage` — 4096
  символов в значении, а в копии кириллица): части — `selfcrm-backup-part-0…N`, метаданные (дата, имя
  файла, число частей, состав копии) — `selfcrm-backup-manifest`. Манифест пишется последним, поэтому
  прерванная запись не портит прежнюю копию, а лишние части прежней копии удаляются. Ключей в облаке
  не больше 1024, то есть копия до ~3,5 МБ — больше приложение предложит сохранить файлом. Имена
  ключей состоят только из разрешённых клиентом символов (латиница, цифры, «_», «-», до 128 символов):
  двоеточие или кириллица для CloudStorage недопустимы и приводят к отказу `STORAGE_KEY_INVALID`,
  поэтому `isValidCloudKey()` (`src/telegram/cloudStorage.ts`) проверяет ключ до запроса к клиенту.
  Облака нет
  вне Mini App и в клиентах Bot API младше 6.9 — тогда остаётся путь с файлом, и в разделе настроек
  вместо кнопок выводится причина: `outside-telegram` — «откройте SelfCRM из бота», `old-client` —
  «обновите Telegram» (признак — `cloudStorageAvailability()`; заглушка `telegram-web-app.js` в
  браузере к Telegram не относится). Без этого отсутствие облачных кнопок выглядело как пропавшая
  функция.
- «Копия файлом в чат с ботом» (Настройки → Резервная копия; только там, где облака нет): кнопка
  «Сохранить и открыть чат» сохраняет файл копии и открывает чат с ботом (`openBotChat`,
  `src/telegram/webapp.ts`). Путь открытия зависит от окружения: в Mini App —
  `WebApp.openTelegramLink` (`openLink` как запасной), в Android-сборке — `window.open(url, '_system')`,
  в браузере — новая вкладка; если ни один способ не сработал, интерфейс показывает адрес бота текстом.
  Сам файл в чат **не отправляется**: Mini App не имеет доступа к истории сообщений и отправляет файл
  пользователь (📎 → Файл) — поэтому текст строки настроек прямо описывает этот шаг.
- Импорт: копия (файл или облако) разбирается и проверяется **до** замены данных — это JSON, это файл
  SelfCRM, версия формата поддерживается, обязательные коллекции на месте, записи не повреждены. Затем
  приложение показывает состав копии (`summarizeBackup`) и предупреждение о замене, и только после
  подтверждения вызывает `applyBackup`. Кнопка «Создать backup и продолжить» сначала сохраняет копию
  текущих данных (в Telegram — в облако, вне его — файлом), и лишь затем заменяет их; «Отмена» не
  меняет ничего.
- Перед импортом и перед сбросом данных приложение само сохраняет копию текущего состояния
  (`selfcrm:data:pre-import-*`, хранятся три последние). Копию можно скачать в
  **Настройки → Резервная копия → Данные до импорта** и вернуть прежнее состояние импортом.
- Если значение в основном ключе (`selfcrm:data`) не читается (повреждён `localStorage`,
  обрыв записи), данные **не затираются**: исходная строка сохраняется под ключом
  `selfcrm:data:corrupt-*`, а на экране настроек появляется предупреждение с кнопкой
  «Скачать повреждённые данные». Приложение при этом стартует с пустой базой и не мешает
  восстановить данные из файла.

## Адреса: Дадата, локальная база и маршрут

Автодополнение адреса (`components/AddressField.tsx`) использует подсказки **Дадаты**
(`api/dadata.ts`, метод `suggest/address`): по мере ввода возвращается полный адрес,
кадастровый номер дома (`house_cadnum`) и координаты (`geo_lat`/`geo_lon`). Метод работает
только по API-ключу (токену); секретный ключ, который нужен серверному `clean/address`,
в клиент не попадает. Подсказки ограничены уровнем дома (`from_bound`/`to_bound`), поэтому
каждая из них — готовый адрес с координатами.

### Ключ Дадаты и сборка

Ключа в исходниках нет. Он подставляется на этапе сборки переменной окружения
`VITE_DADATA_TOKEN`:

- локально — файл `.env.local` (или `.env`), с него собирается APK; оба файла не коммитятся
  (см. `.gitignore`), и `.env` — тот же файл, из которого бот берёт `BOT_TOKEN`;
- для GitHub Actions (веб-версия на Pages) — секрет репозитория `VITE_DADATA_TOKEN`
  в шаге сборки `.github/workflows/deploy-pages.yml`. В `doc9830/selfcrm-tg` секрет уже задан:
  при смене ключа обновите его в Settings → Secrets and variables → Actions и перезапустите
  деплой (Actions → Deploy to GitHub Pages → Run workflow).

Это клиентский ключ сервиса, и он **остаётся внутри собранного приложения** — иначе
пользователю пришлось бы выпускать собственный ключ. Поэтому «скрытие» ключа означает
только отсутствие его в публичном коде репозитория: в APK и в веб-сборке он есть,
и любой может его оттуда извлечь. Для таких ключей в личном кабинете Дадаты стоит включать
ограничение по домену/лимитам.

Если ключ не должен попадать в клиент вообще, нужен посредник на серверной стороне
(например, Cloudflare Worker или функция на хостинге): в бандле остаётся только адрес посредника,
а ключ хранится в его переменных окружения. Цена — внешняя зависимость: при недоступности
посредника подсказки деградируют до локальной базы адресов.

Сборка без ключа (например, сторонний форк) не ломается: `hasDadataToken()` возвращает
`false`, автодополнение работает по локальной базе, а поле показывает, что подсказки
сервиса отключены.

При недоступности сервиса поле автоматически переключается на локальную базу
`db/addresses.ts`:

- **AddressEntry** — кадастровый номер + полный адрес + координаты (`lat`/`lng`).
- `searchAddresses()` — поиск по подстроке адреса или кадастрового номера с сортировкой по релевантности.
- `loadAddresses()/saveAddresses()` — база хранится в `KVStore` под ключом `selfcrm:addresses`;
  если база не задана, используется демо-набор `demoAddresses`.
- `parseAddresses()` — валидация импортируемого JSON (Настройки → Данные → База адресов).

Полноценная выгрузка Росреестра/ФИАС велика для поставки в комплекте, поэтому в приложении —
демо-набор, а реальные данные загружаются пользователем как JSON-массив. Формат записи
универсален и не зависит от источника.

`utils/navigation.ts` строит маршрут:

- Точка назначения задаётся координатами; текстовый адрес идёт подписью в скобках
  (`geo:<lat>,<lng>?q=<lat>,<lng>(<адрес>)`). Яндекс.Навигатор и 2ГИС не умеют искать по
  тексту в `q` — при выборе такого навигатора открывалась карта без точки.
- На Android (Capacitor) `window.open(uri, '_system')` передаёт ссылку ОС, и та показывает
  системный выбор навигатора (Google Maps, Яндекс.Карты, 2ГИС и др.). Если координаты не
  сохранены (адрес вводили вручную), вместо `geo:` открывается ссылка Яндекс.Карт с текстовым
  адресом — она открывается в браузере или приложении Яндекс.Карт и строит маршрут сама.
- В браузере и в Telegram Mini App — маршрут в Яндекс.Картах
  (`https://yandex.ru/maps/?rtext=~…&rtt=auto`, `~` = текущее местоположение). Внутри WebView
  клиента Telegram (мини-приложение и его встроенный браузер — признак `insideTelegramWebView()`)
  ссылку открывает клиент (`openExternalLink` из `telegram/webapp.ts`): `window.open` в WebView
  мини-приложения игнорируется. В обычном браузере, куда `telegram-web-app.js` тоже подключён,
  запрос до клиента не доходит — ссылка открывается новой вкладкой.

Там же `openTel()`/`buildTelUri()` строят `tel:`-URI для звонка: на Android — `_system`,
в браузере — обычный `tel:` на текущей странице.

Для переписки есть `openTelegram()` и `openWhatsApp()`. Интеграции с мессенджерами нет:
приложение только открывает чат по номеру — на Android по схеме приложения
(`tg://resolve?phone=…`, `whatsapp://send?phone=…`), в браузере по веб-ссылке
(`https://t.me/+…`, `https://wa.me/…`), в Mini App — по той же веб-ссылке средствами клиента
Telegram. Номер перед этим нормализуется (`phoneDigits`): «8 900…», «+7 (900)…» и «900…»
приводятся к виду «7900…», иначе ссылка не откроет чат.

## PDF/документы

Чек по завершённому заказу собирается через **pdfmake** (офлайн, встроенный шрифт Roboto
поддерживает кириллицу). В чек попадают: реквизиты исполнителя из настроек, шапка «Заказ №42 от
19.09.2026» (`utils/orders.ts`, `orderHeading`), данные клиента, таблица позиций, итог и — если
платежи уже вносились — строки «Оплачено» и «К оплате». Имя файла — `check-<номер>.pdf`.

Модули разделены по ролям:

- `pdf/receipt.ts` — данные чека (`ReceiptData`) и его упаковка в адрес. Здесь нет ни pdfmake, ни
  обращений к DOM (кроме чтения `window.location` в `receiptUrl`), поэтому упаковку и разбор
  проверяют тесты. Позиции хранятся снимком (название, количество, цена) — как в заказе. Тут же
  адрес с просьбой «скачать файл»: `receiptDownloadUrl()` дописывает признак `dl=1`, а
  `receiptWantsDownload()` его читает.
- `pdf/documents.ts` — сам документ: `receiptDocDefinition()` (описание для pdfmake),
  `receiptPdfFile()`, `downloadReceiptPdf()` и точки входа для экранов — `shareOrderReceipt()`
  (кнопка «Чек (PDF)» в карточке заказа) и `saveReceiptPdf()` (кнопка «Сохранить PDF» на странице
  чека).
- `pdf/receiptDelivery.ts` — выбор способа доставки: `planReceiptDelivery()` (чистая функция),
  `canShareFiles()`, `shareReceiptLink()` и `copyReceiptLink()`.

Способов доставки четыре, и выбирается один — первый подходящий:

1. `native` — Android-сборка: PDF пишется во временный каталог (`@capacitor/filesystem`,
   `Directory.Cache`) и открывается системным меню «Поделиться» (`@capacitor/share`).
2. `link-share` — Telegram Mini App: вместо PDF уходит **ссылка на страницу чека**.
   Данные чека лежат в самом адресе (`#/receipt?d=…`), поэтому у получателя страница собирает
   документ без сервера и без базы отправителя. Выбор чата открывает клиент Telegram
   (`https://t.me/share/url?url=…&text=…` через `openExternalLink`).
3. `file-share` — клиент умеет `navigator.share` с файлами (проверяется пробным PDF через
   `navigator.canShare`): в системное меню уходит сам файл.
4. `file-download` — обычный браузер: blob + `<a download>`.

Telegram проверяется раньше Web Share API намеренно: в WebView на Android `navigator.share` и
`navigator.canShare` объявлены и на пробный PDF отвечают «да», но системного меню у WebView нет —
промис не завершается, и нажатие «Чек (PDF)» выглядело как «ничего не произошло» (на iOS тот же
путь работал, потому что там файлы в Web Share API не поддержаны и выбиралась ссылка).

Если клиент обещал отдать файл, но отказал (например, системное меню требует нажатия в том же
такте, а PDF собирался асинхронно), путь продолжается скачиванием — в браузере оно нажатия не
требует.

Почему из мини-приложения уходит ссылка, а не файл: клиент Telegram игнорирует и blob-ссылки, и
`<a download>`, а `WebApp.downloadFile` принимает только адреса `https:` — то есть готовый файл,
собранный на странице, отдать нечем. Ссылка этот тупик обходит и одинаково работает на iPhone,
Android и в браузере; в чат она отправляется с подписью «Чек по заказу №42 от 19.09.2026». Если
выбор чата не открылся, ссылка ложится в буфер обмена, а под кнопкой «Чек (PDF)» остаётся
«Скопировать ссылку» (`copyReceiptLink`) — отправитель видит результат в любом случае.

Скачать сам PDF из мини-приложения тоже можно — руками отправителя, через браузер. Под кнопкой
«Чек (PDF)» появляется «Скачать PDF» (`screens/OrderDetail.tsx`), а на странице чека внутри Telegram
основная кнопка называется «Скачать PDF в браузере»: обе открывают тот же адрес чека в браузере
(`openExternalLink` → `WebApp.openLink`) с признаком `dl=1` (`receiptDownloadUrl`). В браузере
признак читает `receiptWantsDownload()`, и страница чека скачивает PDF сразу, без второго нажатия
(`autoDownload` в `screens/ReceiptView.tsx`) — при этом кнопка «Сохранить PDF» на ней остаётся на
случай, если браузер загрузку отклонил. Файл всё равно сначала попадает в «Загрузки» браузера,
откуда его прикрепляют к сообщению руками: мини-приложение отдать файл не может, но путь без
сервера и без второго устройства работает.

Данные в адресе упакованы экономно, потому что ссылка уходит в сообщение: короткие имена полей,
позиции массивами, JSON → `deflate-raw` (`CompressionStream`) → base64url. Сжатие есть не во всех
клиентах и само может отказать (например, `CompressionStream` объявлен, а `deflate-raw` не
поддержан), поэтому у нагрузки есть признак: `1.` — со сжатием, `0.` — обычный JSON (ссылка
длиннее, но рабочая). Разбор чужой ссылки проверяет каждое поле и на любой непонятной нагрузке
отвечает `null` — страница показывает «Ссылка не читается» вместо пустого документа. Перед
отправкой сверяется длина (`RECEIPT_LINK_LIMIT`): у сообщения Telegram предел 4096 символов, и
обрезанная ссылка хуже понятной ошибки.

Страница чека — `screens/ReceiptView.tsx`, маршрут `#/receipt?d=<нагрузка>` (`App.tsx`, разбор
параметра — `receiptPayloadFromQuery`). Экран рендерит тот же состав строк, что и PDF, и повторяет
действия карточки заказа: «Сохранить PDF», «Печать» (в iOS печать сохраняет PDF в «Файлы») и
«Поделиться». Своя оболочка без нижнего меню и значков разделов — чек открывают и получатели
ссылки, а не только владелец CRM; правила печати (`@media print` в `index.css`) оставляют на
бумаге только сам документ. «Сохранить PDF» на этой странице — `saveReceiptPdf()`: в Android-сборке
системное меню «Поделиться», в браузере скачивание, а внутри Telegram (мини-приложение и его
встроенный браузер — признак `insideTelegramWebView()`) файл отдать нечем, поэтому основная кнопка
там называется «Скачать PDF в браузере» и открывает эту же страницу с признаком `dl=1`, а
«Сохранить PDF» показывается только в обычном браузере.

`pdf/documents.ts` импортируется лениво (`import()` в `OrderDetail.tsx` и `ReceiptView.tsx`),
поэтому pdfmake и встроенные шрифты не попадают в основной бандл и загружаются только при
формировании или сохранении чека.

На Android PDF пишется во временный каталог через `@capacitor/filesystem` и открывается
системным меню «Поделиться» через `@capacitor/share`; в браузере — обычное скачивание.

## Сортировка списков

Варианты сортировки заданы в `state/SortContext.tsx` (`SORT_SCOPES`): ключ — первый сегмент
маршрута (`orders`, `products`), значение — набор вариантов и вариант по умолчанию. Значения
хранит `SortProvider`, поэтому выбранная сортировка сохраняется при переходах между разделами.

Интерфейс — значок со стрелочками в шапке (`components/SortMenu.tsx`): кастомный (не системный
`<select>`) список открывается поверх содержимого, закрывается по нажатию вне меню и по Escape.
Значок показывается только на экранах-списках (`sortScopeForRoute()` возвращает область для
маршрута из одного сегмента) и подсвечивается, когда выбран не вариант по умолчанию.
Экраны читают значение через `useSortValue('orders' | 'products')` и сортируют список сами.

## Обновления

`src/version.ts` хранит текущую версию приложения (`APP_VERSION`) и репозиторий, у которого
запрашивается последний релиз (`GITHUB_REPO = doc9830/selfcrm-tg`), `src/updates.ts` —
проверку обновлений: запрос к GitHub API (`releases/latest`), сравнение семантических версий и
открытие ссылки на релиз (через `@capacitor/browser`).

Проверка запускается двумя способами:

- автоматически при открытии приложения — `components/UpdateToast.tsx` рендерится в `App.tsx`;
  если версия новее, снизу появляется полупрозрачное уведомление. Нажатие ведёт на
  `/settings?section=updates` (константа `UPDATE_SECTION_PATH`), крестик запоминает версию
  в `localStorage` (`selfcrm:update-dismissed`) и больше её не показывает. Ошибки сети
  игнорируются, чтобы проверка не мешала работе офлайн;
- вручную — кнопка в **Настройки → Обновления**. При переходе по уведомлению экран настроек
  прокручивается к блоку обновлений, подсвечивает его и сразу запускает проверку.

**В Mini App проверки нет.** Установка обновления — это скачивание APK и запуск системного
установщика, чего в WebView Telegram нет. Поэтому и уведомление (`UpdateToast`), и блок
«Обновления» в настройках включаются только на нативной платформе
(`Capacitor.isNativePlatform()`); в Mini App показывается текущая версия и подпись, что страница
всегда загружается с GitHub Pages последней. Заодно исчезают лишние запросы к GitHub API при
каждом запуске.

Описание релиза выводится с переносами (`overflow-wrap: anywhere`), поэтому длинные строки
(например, хеш APK) не выходят за пределы экрана. Текст описания один и тот же для приложения
и для Telegram, поэтому он пишется коротко — чтобы пост в канале читался одним сообщением
(правило и чек-лист: [docs/TELEGRAM_RELEASES.md](./docs/TELEGRAM_RELEASES.md), «Правило одного
поста»; в репозитории Mini App автопубликация отключена — workflow лежит рядом как
`telegram-release.yml.disabled`, а страницу публикует `deploy-pages.yml`).

## Главный экран

Экран **Главная** (`screens/Dashboard.tsx`, маршрут `/`) начинается с двух плашек-кнопок:

- **Активные заказы** — количество заказов в статусах «Новый» и «В работе»;
  по нажатию открывается вкладка «Заказы» с фильтром «Активные» (`/orders?filter=active`);
- **Выручка за месяц** — сумма завершённых заказов текущего месяца (`summarizeOrders` по
  диапазону `periodRange('month')`); по нажатию открывается статистика за тот же период
  (`/statistics?period=month`), поэтому плашка и экран показывают одно и то же число.

Под плашками идёт блок **«Напоминания»** (если активные напоминания есть): он собирает ближайшие
сроки из всех заказов через `db.getReminders()`, группирует их (`utils/reminders.ts`:
`groupReminders` — «Просрочено», «Сегодня», «Завтра», дальше дата) и ограничивает пятью
строками (`limitReminderGroups`, остальные остаются в карточках заказов). Тап по строке
открывает связанный заказ (`/orders/<id>`), чекбокс отмечает выполнение
(`db.toggleReminder`) — напоминание исчезает из активных. Отменённые заказы в блок не попадают.

Блоки главного экрана лежат в контейнере `.dash`, соседние блоки разделены отступом 20px
(`.dash > * + *`) — без него карточка напоминаний прилипала к плашкам.

Параметры адреса разбираются в `utils/links.ts` (`OrderFilter`, `ORDER_FILTERS`,
`matchesOrderFilter`, `orderFilterFromQuery`, `statisticsLink`, `statisticsPeriodFromQuery`) —
модуль не зависит от React и покрыт unit-тестами. Фильтр «Активные» — это группа статусов
(`isActiveStatus` из `types.ts`), а не отдельный статус заказа; чипы на экране «Заказы»
строятся из того же списка `ORDER_FILTERS`, поэтому фильтры плашки и вкладки не расходятся.
Неизвестное значение параметра трактуется как «Все», а вкладка «Заказы» без параметра
показывает все заказы: так возврат с карточки заказа или из нижнего меню всегда даёт полный
список.

## Карточка заказа: номер, оплата и прибыль

Экран заказа (`screens/OrderDetail.tsx`) начинается с шапки: номер заказа, панель статуса,
сумма и **полоса оплаты**. Статус переключается сегментами «Новый / В работе / Завершён /
Отменён» (`.status-picker`, активный сегмент красится классом `.badge-*` по `statusTone`),
поэтому отдельных кнопок «Завершить»/«Отменить» внизу карточки нет: смена статуса — один тап.
Для «Отменён» запрашивается подтверждение: отмена возвращает товары на склад и убирает заказ
из выручки. Состояние оплаты не хранится отдельным
полем — оно вычисляется из суммы
заказа и суммы платежей (`utils/payments.ts`: `orderPaid`, `paymentState`, `orderPaymentState`):

- `unpaid` — платежей нет, `partial` — внесено меньше суммы, `paid` — ровно столько,
  `overpaid` — больше. Полоса показывает долю оплаты (`percent`) и меняет цвет, а под ней
  подсказка с остатком.

Платежи (`Payment`) вводятся в окне «Добавить оплату»: сумма, комментарий и кнопка
«Полностью», которая подставляет остаток. Платежи не влияют на склад — сохранение заказа
с платежом не создаёт движений товара.

Позиции заказа показывают прибыль: `orderCost`/`orderProfit` (`utils/stats.ts`) считают
себестоимость по снимку `item.cost`, поэтому прошлые заказы не зависят от текущих цен каталога.

## Повтор заказа

В карточке завершённого или отменённого заказа (проверка — `canRepeatOrder` из `utils/orders.ts`)
есть кнопка **«Повторить заказ»**. Она ведёт на `/orders/new?repeat=<id>` (`repeatOrderLink`,
`repeatOrderFromQuery` в `utils/links.ts`) — это та же форма нового заказа, но заполненная
образцом. Адрес, как и `?client=`, — часть контракта экрана: ссылку можно открыть заново, а
отмена повтора возвращает к заказу-образцу.

Черновик собирает `Database.createRepeatDraft(source)`: новый `id` и номер, текущая дата, статус
«Новый», пустой комментарий, тот же клиент и **копии** позиций со снимком цены, количества и
себестоимости — прибыль нового заказа считается по цифрам старой сделки, а не по текущему
каталогу. Данные прошлой сделки не переносятся: оплаты и статус оплаты, напоминания, статус,
история движения склада и чек. Сам прежний заказ функция только читает — он не меняется.

Сохранение формы обычное (`saveOrder`), поэтому это новый заказ со своим списанием: остатки
меняются ровно как при ручном создании (движение «Заказ №N», услуги склад не двигают), а после
сохранения приложение открывает карточку нового заказа, где видны новый номер и статус.

## Напоминания по заказам

Напоминание — часть заказа, а не отдельная сущность: в карточке заказа между разделом
**Оплата** и кнопкой **Чек (PDF)** стоит блок «Напоминания» со списком и кнопкой «Напомнить»
(`screens/OrderDetail.tsx`, окно `ReminderModal`). Планировщика в приложении нет — главный
экран только собирает ближайшие сроки из всех заказов.

- **Вид** (`ReminderKind`): звонок, оплата, товар, другое. Вид задаёт иконку и подсказку текста
  («Позвонить клиенту», «Напомнить об оплате», «Проверить наличие/получение товара»).
  Подсказка подставляется, пока пользователь не ввёл свой текст (`reminderTextForKind`:
  чужую или пустую подсказку заменяем, свой текст сохраняем). Для вида «Другое» подсказки нет,
  поэтому текст обязателен (`reminderTextError`).
- **Срок.** «Сегодня» и «Завтра» берут ближайший круглый час (`defaultReminderDueAt`) — так
  напоминание не оказывается просроченным сразу. Вариант «Выбрать дату и время» собирается из
  полей `date`/`time` (`reminderDueAtFromInputs`); срок в прошлом создать нельзя.
- **Список в заказе.** Активные напоминания идут сверху по сроку, выполненные — ниже как
  история (`sortOrderReminders`). Чекбокс отмечает выполнение, корзина удаляет напоминание.
- **Сроки и статусы** считаются в `utils/reminders.ts`: `reminderGroupKey` (просрочено «раньше
  сегодня» — приоритетнее, поэтому просроченное показывается отдельной группой и первым),
  `reminderWhenLabel` («Сегодня, 18:00», «25.09, 09:00»).
- **Данные.** `Database.addReminder` / `toggleReminder` / `deleteReminder` правят массив
  `order.reminders` и сохраняют базу; склад не затрагивается (проверено тестом).
  `getReminders()` отдаёт активные напоминания вместе с заказами (копии через `cloneOrder`),
  пропуская отменённые заказы, `getOrderReminders(orderId)` — список для карточки заказа.
  Форма заказа платежи и напоминания не редактирует: их переносит `applyOrderForm`
  (`utils/orders.ts`) — без этого сохранение правок стирало бы напоминания.

## Статистика

Экран **Статистика** (`screens/Statistics.tsx`, маршрут `/statistics`, открывается кнопкой
«Статистика» на главной или плашкой «Выручка за месяц») показывает показатели за
выбранный период: выручку, сумму «в работе», прибыль, число заказов, средний чек, себестоимость
проданного, разбивку по статусам, топ-5 товаров и услуг и топ-5 клиентов. Прибыль — это выручка
минус себестоимость (`orderProfit`): наценка по товарам плюс оказанные услуги. Период задаётся
пресетами («Сегодня», «7 дней», «Месяц», «Квартал», «Год», «Всё время») или произвольным
диапазоном дат; начальный период может прийти из адреса (`#/statistics?period=month`).

Фильтрация и агрегация вынесены в чистые функции `utils/stats.ts` (`periodRange`,
`filterOrdersByRange`, `summarizeOrders`, `orderCost`, `orderProfit`, `groupRevenue`,
`groupItemRevenue`) — они не зависят от `Database` и покрыты unit-тестами. **Терминология:**
«выручка» — сумма завершённых заказов, «в работе» (`inWork`) — новые и принятые в работу,
отменённые не попадают никуда. Прибыль, средний чек и топы тоже считаются по завершённым
заказам: незавершённый заказ — это ещё не заработанные деньги, хотя товар по нему уже списан
со склада (`committedQty` учитывает все статусы, кроме `cancelled`). Экран пересчитывается
через `useMemo` по
зависимости от `db` и `version` из `DataContext`, поэтому обновляется сразу после изменения
данных.

## Состояние и роутинг

- `state/DataContext.tsx` — провайдер, отдаёт экземпляр `Database` и функцию
  `refresh()` (инкремент версии → перерисовка потребителей).
- `state/SortContext.tsx` — значения сортировки списков (`orders`, `products`) для значка
  в шапке; хук `useSortValue(scope)` читает текущий вариант на экране.
- `state/ThemeContext.tsx` — тёмная/светлая тема: переключает `data-theme` на `<html>`,
  сохраняет выбор в `localStorage` (`selfcrm:theme`) и обновляет `theme-color`. До отрисовки
  тему выставляет инлайн-скрипт в `index.html`, чтобы не было «мигания» светлой темы.
- `router.ts` — hook `useRoute()`, парсит `window.location.hash` в сегменты и query-параметры
  (разбор адреса — `parseRoute`, им же пользуются и экраны, и навигация «назад»).
- `App.tsx` сопоставляет сегменты маршрута с экранами.
- Маршрут `#/receipt?d=…` (`App.tsx` → `screens/ReceiptView.tsx`) — страница чека по ссылке:
  чек приезжает в самом адресе, поэтому её открывает любой получатель, и в приложении у неё своя
  оболочка без нижнего меню (`pdf/receipt.ts`, `pdf/documents.ts`).
- `utils/back.ts` — единственное место с правилами «куда ведёт Назад»: `headerBackTarget`
  (стрелочка в шапке, `null` — стрелочки нет) и `backTarget` (системная кнопка Android:
  как стрелочка, а с верхнего уровня — на «Главную»). Стрелочка и аппаратная кнопка берут
  значение отсюда, поэтому не расходятся.
- `components/SystemBack.tsx` — обработчик системной кнопки «Назад» (жест «назад» в том числе):
  подписывается на событие `backButton` плагина `@capacitor/app` и сначала отдаёт нажатие
  открытым окнам и меню (событие `selfcrm:back` — на него подписаны `Modal` и `SortMenu`),
  затем идёт по `backTarget`, а на «Главной» показывает подсказку и закрывает приложение
  по второму нажатию. В браузере обработчик не подключается.

## Безопасность

- **Проверка подписи обновления.** Перед запуском системного установщика
  `AppInstallerPlugin.verifyUpdateApk()` читает скачанный APK и сравнивает имя пакета и
  SHA-256 отпечатки сертификатов подписи с установленным приложением. Несовпадение или
  нечитаемый файл — установка не запускается, пользователь видит понятное сообщение.
  Android и сам не позволит поставить APK с другой подписью, но проверка срабатывает раньше
  и без участия системы.
- **FileProvider.** `android/app/src/main/res/xml/file_paths.xml` открывает только внутренний
  кэш приложения (`cache-path`): там лежат PDF-чек и скачанный APK обновления. Доступ к
  внешнему хранилищу приложению не нужен и не выдаётся.
- **Резервное копирование ОС отключено.** `android:allowBackup="false"` в `AndroidManifest.xml`:
  данные не уходят в облачный бэкап Google и не переносятся через `adb backup`. Копии делает
  сам пользователь (Настройки → Резервная копия).
- **CSP.** В `index.html` задана `Content-Security-Policy`: скрипты и стили — только свои
  (`'unsafe-inline'` нужен для инлайн-скрипта темы) плюс `https://telegram.org` — обязательный
  официальный `telegram-web-app.js`; сетевые запросы — только к `api.github.com` (проверка
  обновлений) и `suggestions.dadata.ru` (подсказки адресов), объекты запрещены
  (`object-src 'none'`), `base-uri` и `form-action` ограничены.
- **Telegram: токен бота не попадает в приложение.** Mini App не обращается к Bot API, поэтому
  `BOT_TOKEN` не нужен ни на странице, ни в сборке: он читается только локальным
  `scripts/telegram-bot.mjs` из переменной окружения или `.env` (файл вне git). Переменной с
  префиксом `VITE_` для токена не существует — иначе он оказался бы в бандле, который
  скачивает любой пользователь.
- **Telegram: адрес Mini App живёт в кнопке меню.** `WEBAPP_URL` / `--webapp-url` нужны только
  боту; на страницу адрес не влияет. Общую кнопку меню ставит `npm run bot:setup`, в конкретном
  чате — сам запущенный бот при первом сообщении: Telegram применяет общую настройку не сразу и
  может ответить `ok`, оставив прежнее значение, поэтому скрипт перечитывает результат.
- **Telegram: непроверенные данные не используются как ключи.** `initData` подписывает Telegram,
  но проверить подпись можно только на сервере, которого у SelfCRM нет. Поэтому `initDataUnsafe`
  (имя и `id` пользователя) применяется лишь для подписи резервной копии и отображения; данные
  CRM адресуются собственными идентификаторами и от Telegram не зависят.
- **Ключ подписи.** `android/selfcrm-release.keystore` и `android/keystore.properties` лежат
  вне git (`android/.gitignore`) и имеют права `600`. Резервную копию ключа нужно хранить
  отдельно от проекта: без него невозможно выпустить обновление поверх установленной версии.

## Версионирование данных

`DatabaseSnapshot.version` зарезервирован для будущих миграций схемы. Это не то же самое, что
`version` в файле резервной копии: там нумеруется **формат файла** (см. «Резервное копирование»).
Файл, в котором версии нет или она старше текущей, дополняет `Database.migrate()` при импорте.
